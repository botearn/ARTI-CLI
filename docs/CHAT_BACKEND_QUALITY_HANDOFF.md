# ARTI Chat 后端质量优化交接

- 日期：2026-07-30
- 面向团队：ARTI 主 repo / `v1-chat` 维护团队
- 来源：ARTI CLI `0.4.4` 生产链路实测
- 范围：回答质量、响应契约、Token 可观测性与质量评测
- 不包含：CLI 终端渲染、Session 本地存储、Credits 决策

## 1. 假设

本文基于以下边界：

- 主 repo 负责 `v1-chat`、系统提示词、模型调用、建议问题、SSE 事件和服务端 Token usage。
- ARTI CLI 是瘦客户端，不在本地判断金融结论、不裁剪模型正文、不估算 Token 或 Credits。
- 扣费、缓存和模型路由继续由后端决定，本文不改变计费模型。

如果实际归属不同，应先调整负责人，不应把内容质量规则下沉到 CLI。

## 2. 实测数据

### 2.1 单轮概念问题

输入：

> 请用两句话解释市盈率，并说明它为什么不能单独用于判断股票便宜还是贵。

结果：

- 约 10 秒收到首段，23.1 秒完成。
- 回答扩展为四部分长文，没有遵守“两句话”。
- 使用了“公用事业 10–15 倍”“科技成长股 30–50 倍”等经验区间，但没有时间、市场或来源。
- 把“按当前盈利水平多少年回本”作为直观解释，但没有说明利润不等于股东现金流。

### 2.2 连续两轮计算

第一轮：

> 假设公司股价100元、每股收益5元，请计算市盈率，并用一句话解释结果。

后端正确计算 `100 ÷ 5 = 20 倍`，但额外判断“处于市场常见的合理估值区间”。在缺少行业、增长率、利率和盈利质量时，这个判断依据不足。

第二轮：

> 如果每股收益下降到4元、股价不变，请沿用刚才的数据重新计算，只回答新市盈率和相对上一轮的变化方向。

后端正确引用历史并计算 `100 ÷ 4 = 25 倍`，连续上下文成立；但仍追加两个建议问题，没有遵守“只回答”。

### 2.3 Token

| 轮次 | 输入 | 输出 | 总计 |
|---|---:|---:|---:|
| 第一轮简单计算 | 9,027 | 254 | 9,281 |
| 第二轮追问 | 4,685 | 113 | 4,798 |
| 会话累计 | 13,712 | 367 | 14,079 |

简单计算携带 9,027 个输入 Token，需检查系统提示词、无关工具说明和产品上下文是否过重。过量上下文不只增加成本，也可能削弱用户指令的优先级。

### 2.4 JSON 探活

输入 `只回答 JSON_OK` 时，后端将其识别为金融域外请求并拒绝。协议正常，但通用探活语句不适合作为 Chat smoke test；后续测试应使用明确的金融问题。

## 3. 顶层规则

### R1：正文忠实于用户的输出约束

- “一句话”“只回答数字”“不要建议”等显式约束必须优先于默认回答模板。
- 用户要求简短时，不应固定追加解释、免责声明或建议问题。
- 必须保留的风险披露应尽量结构化返回，不应静默破坏用户指定格式。

### R2：金融事实、推断和行动建议分层

- 公式计算属于事实。
- “合理估值区间”“便宜或昂贵”属于需要前提和证据的推断。
- “买入、卖出、持有”属于行动建议。
- 缺少行业、增长、利率、盈利质量或数据时间时，只能给计算结果和缺失条件，不能补出确定性判断。

### R3：实时结论必须带数据边界

涉及价格、估值、财报或市场状态时，回答必须能够说明：

- 数据时间 `asOf`
- 数据来源
- 币种与市场
- 关键假设
- 结论失效条件

纯概念问题不要求强行添加来源。

### R4：正文、建议和遥测分离

正文、建议问题、模型信息和 Token usage 应是独立数据。客户端不应从 Markdown 或 `[建议]...[/建议]` 中反向解析协议。

### R5：服务端 usage 是唯一权威

- 后端返回 provider 实际 usage，不允许客户端估算。
- usage 与 Credits 分离。
- 能获得模型上下文窗口时返回 `contextWindow`；不能获得时明确省略，不伪造默认值。

## 4. 当前差距

| 差距 | 用户影响 | 归属 |
|---|---|---|
| 明确长度约束未被遵守 | 回答冗长、失去控制感 | 后端提示词与响应策略 |
| 建议问题混在正文 | CLI 无法尊重“只回答” | 后端响应契约 |
| 缺少前提时仍判断合理估值 | 降低金融可信度 | 后端金融规则 |
| 简单问题输入 Token 过高 | 延迟、成本和指令稀释 | 后端上下文装配 |
| 外层调用可能收不到 usage | 自动化可观测性不足 | 后端事件完整性 + 客户端 capability |
| usage 缺少 `contextWindow` | 无法计算上下文占用 | 后端模型元数据 |
| 没有固定质量回归集 | 提示词改动不可验证 | 后端测试与观测 |

## 5. 后端产出物

### 5.1 回答策略

主 repo 应建立最小回答策略，不建议继续单纯叠加系统提示词：

1. 识别用户的格式约束：长度、只输出某字段、是否允许建议。
2. 根据问题类型选择回答预算：简单计算、概念解释、实时数据、估值判断。
3. 在生成前确定允许输出的区块。
4. 生成后验证是否出现无依据判断或违反显式格式。

不建议让 CLI 截断正文。CLI 无法知道被删除内容是否改变金融语义。

### 5.2 SSE 响应契约

建议对声明支持新事件的客户端，将建议问题从正文中拆出：

```text
event: message.delta
data: {"content":"新市盈率为 25 倍，较上一轮上升。"}

event: suggestions
data: {"items":[]}

event: usage
data: {
  "requestId":"req_xxx",
  "model":"claude-sonnet-4-6",
  "inputTokens":4685,
  "outputTokens":113,
  "cachedInputTokens":0,
  "totalTokens":4798,
  "contextWindow":200000
}

event: message.done
data: {"requestId":"req_xxx","model":"claude-sonnet-4-6"}
```

请求 capability 可采用加法扩展：

```json
{
  "clientCapabilities": {
    "usageEvents": true,
    "suggestionEvents": true
  }
}
```

行为：

- 客户端声明 `suggestionEvents` 时，不再把 `[建议]` 标签写入 `message.delta`。
- 用户明确要求“只回答”或“不要建议”时，返回空数组。
- 未声明新 capability 的旧客户端保持现有协议，迁移完成后再决定是否下线旧格式。

### 5.3 金融表达规则

以下内容应进入后端质量规则或回答模板：

- P/E 可以解释为价格相对每股收益的倍数，但“多少年回本”只能标注为静态直觉，不得当作实际回收期。
- 不能仅凭一个 P/E 数字判断合理、便宜或昂贵。
- EPS 下滑导致 P/E 上升时，应区分“数学上的估值倍数上升”和“盈利恶化”。
- 行业估值区间必须有数据时间和来源；没有来源时不输出具体区间。
- 回购可能提高 EPS，但不应笼统表述为“操纵”，应说明经营利润与每股口径的区别。

### 5.4 Token 与上下文审计

对简单计算的 9,027 输入 Token 做分段记录：

```text
systemPromptTokens
policyTokens
toolDescriptionTokens
retrievedContextTokens
conversationTokens
artifactTokens
totalInputTokens
```

建议先做消融测试，再决定删减：

- 移除无关工具说明是否影响回答。
- 按问题类型选择提示词片段是否改善遵循率。
- 建议问题是否可以独立生成或仅在需要时生成。
- 长期不变的系统内容是否获得 provider prompt cache。

不建议在没有数据前设定一个武断的绝对 Token 上限。

### 5.5 质量评测集

主 repo 至少覆盖以下用例：

| 用例 | 通过条件 |
|---|---|
| “只用一句话解释 P/E” | 正文只有一句话 |
| “只回答数字” | 不追加解释、建议或标题 |
| 缺少行业信息时判断 20x 是否便宜 | 明确缺少条件，不下确定结论 |
| EPS 从 5 降到 4 的连续追问 | 正确引用 100 元股价和上一轮 20 倍 |
| 实时股价问题 | 包含数据时间和来源 |
| 概念问题 | 不强行添加无关引用 |
| “不要建议问题” | suggestions 为空 |
| usage capability | 返回可解析、内部一致的 usage |

每次评测记录：

```text
promptVersion
model
requestId
latency
inputTokens
outputTokens
instructionFollowing
unsupportedClaims
financialPrecision
```

确定性检查优先用代码完成，例如句子数、纯数字输出、SSE schema 和 usage 加总；金融严谨性再使用人工抽检或模型裁判。

## 6. 推荐 PR 顺序

### PR 1：回答规则与最小评测集

- 修复显式格式约束。
- 禁止缺少依据的合理估值判断。
- 加入上述核心回归用例。

### PR 2：独立 suggestions 事件

- 增加 capability。
- 将建议与正文分离。
- 保留可控的兼容迁移期。

### PR 3：usage 与上下文审计

- 补齐稳定的模型、request ID 和 usage 事件。
- 能确定时返回 `contextWindow`。
- 记录输入 Token 构成并做消融验证。

## 7. 验收标准

交付完成时，应能用生产等价环境证明：

1. 显式要求一句话或只回答结果时，不再追加固定区块。
2. 缺少估值前提时不输出“合理、便宜、昂贵”等确定判断。
3. 连续两轮计算保持上下文正确。
4. 新客户端能分别消费 answer、suggestions 和 usage。
5. usage 数值内部一致，且不与 Credits 混淆。
6. 质量评测进入主 repo CI，提示词或模型变更时自动回归。

## 8. 非目标

- 不在 CLI 侧实现金融规则。
- 不在 CLI 侧估算 Token 或 Credits。
- 不在本次优化中修改计费、套餐或模型路由。
- 不因简单问题强制进入 Agent Harness。
